# Propuesta de consolidación para un repositorio privado

## Base y criterio de entrada

Usar `main` en `a96ba794a6171a325836a5a56bf1c9392dbd8482` como referencia reproducible. Conservar la demo en `3a2850060c96b2f7eaeae613c8a402aa9486c079` como referencia de aceptación. El contenido de `desarrollo/ola1` queda candidato a integración tras validar sus cambios por alcance, construir desde DBD y comprobar Excel. La apertura del destino, la forma de importar historia y cualquier publicación requieren autorización específica.

## Secuencia propuesta

1. **Preparar procedencia e inventario.** Usar el manifiesto Git para documentar cada origen, ruta, licencia y decisión de inclusión. Conservar evidencia de origen por SHA sin incorporar por defecto material de terceros, credenciales, datos reales o archivos de prueba repetidos.
2. **Restaurar reproducibilidad.** Elegir fuentes únicas para DBD, datos iniciales, casos y pruebas. Verificar la generación desde una carpeta limpia y distinguir las salidas de demostración. Registrar Python, dependencias, herramientas de Windows y versión de Office sin depender de los archivos binarios que la rama ya traía.
3. **Recuperar los cambios coherentes.** Revisar D12, D1 y el arreglo de FK como una secuencia motivada por el contrato de empresa. Evaluar OPERAR MES después, con su plantilla y pruebas. Importar por ruta las directrices finales, lecciones ORIA y deuda. Usar la prueba de seis meses para comparar rendimiento; preservar el diseño I-9 como pendiente.
4. **Cerrar el riesgo de capa y persistencia.** Probar separación por empresa de la cadena completa, filtros por periodo, cuadre de cuentas, rollback de cierre inducido y linaje de cada resultado publicado. Revisar conciliación REAL/CONTABLE y versionar la matriz MCD→DBD→prueba.
5. **Fijar la puerta de aceptación.** Incluir pytest, construcción estricta, regresión histórica, O-1 con umbral de aceptación, oráculos manuales y prueba Excel con paridad; exigir explícitamente que las capacidades declaradas de negocio tengan un estado verificable. Medir carga local durante seis meses con parámetros representativos y simular respaldo y restauración.
6. **Tomar la decisión tecnológica después de la equivalencia.** Comparar mantener Excel, mantener Excel como interfaz con Python y SQLite, o usar un producto local independiente. Evaluar distribución offline, compatibilidad, concurrencia, precisión monetaria y costo de migración antes de una aprobación. El SQLite histórico del repositorio no constituye un sistema operativo equivalente.

Cada lote debería consignar fuente, revisión independiente, diferencias aceptadas, pruebas y mecanismo de retorno. Las ramas históricas son archivo de consulta. La selección documental y de código se basa en cambios revisados por componente.
